# 框架验证与晋级计划

## 1. 当前状态

`0.10.0-candidate.2` 是根据首个真实项目反馈修正的候选规范。它尚未完成跨项目实际开发效果验证，不能宣称适用于所有项目。

## 2. 验证对象

- 路线是否正确且不过度治理；
- 阶段、系统视图和模板是否防止关键遗漏；
- 模块交互与精化边界是否足以支持并行开发；
- 团队约束是否正确影响分工而不扭曲业务边界；
- 自验是否能发现矛盾、断链和过度约束；
- 不同模型或开发者是否能独立理解同一准备包；
- 开发阶段的重新猜测、返工和契约重定是否降低。

## 3. 验证步骤

### A. 结构审计

- 目录、链接、模板和Schema完整；
- 核心文档之间无明显冲突；
- 没有Skill、Hook或编码执行要求泄漏到规范本体；
- 版本、状态和停止线清楚；
- 项目内输出位置、包身份和最小清单一致且可检查。
- 写入前路径预检能够拒绝相邻同名项目；
- 来源治理能够拒绝旧资料污染；
- 澄清回写和虚假 Ready 具有自动负例。
- 声明复杂关系却没有可见图时机械拒绝；通信、事务与失败恢复是否充分由语义审查判定。
- 标准/完整路线只有 Markdown 图表源码、没有可直接阅读的呈现版时能够被拒绝。

### B. 固定案例评测

独立执行并逐案记录 `evals/cases/` 中轻量、标准、跨模块、数据迁移、团队约束、无效输入、路径错误、旧资料污染、澄清回写、虚假 Ready、通信模型缺失和未渲染交付案例。

### C. 隔离上下文复读

由未参与框架设计的新模型或人员：

1. 只读取入口和适用模板；
2. 选择路线；
3. 对固定案例生成准备包；
4. 说明何时停止以及哪些决策仍需人工确认。

### D. 真实试点

至少覆盖：

- 一个轻量修改；
- 一个标准单模块功能；
- 一个跨模块功能；
- 一个外部接口或数据变更；
- 一个带团队约束的拆解。

### E. 效果记录

- 开发前发现的问题；
- 开发中重新定义需求或契约的次数；
- 因准备包缺失产生的返工；
- 非设计者理解准备包所需补充问题；
- 流程耗时和被裁剪的内容；
- 过度约束模型执行的条目；
- 未被自验发现的遗漏。

## 4. 晋级要求

候选版在限定范围内晋级 `1.0.0` 前必须满足：

1. 结构审计无未解决的严重缺陷；
2. 固定案例均达到预期路线和硬门；
3. 隔离上下文可以独立完成路线判断与关键产物；
4. 真实试点覆盖声明的任务范围；
5. 关键需求追踪链完整；
6. 没有高后果需求被错误降级；
7. 轻量任务没有被不必要地扩展为完整流程；
8. 团队约束没有扭曲业务边界；
9. 没有把执行器、Skill或工具选择固化为前置要求；
10. 有独立复核、已知限制和适用范围声明；
11. 维护者和试点责任人接受流程成本、产品结果责任和正式适用范围。

## 5. 结论类型

- `通过`：在声明范围内晋级正式版；
- `有条件通过`：只在部分路线、项目或风险范围内使用；
- `未通过`：存在框架设计缺陷，退回重构；
- `证据不足`：没有证明失败，也没有足够证据正式采用。

## 6. 框架回归

每次发现“框架本应提前发现但没有发现”的问题，都应形成新的固定案例。框架修改后重新运行受影响案例，并记录版本、修正和验证证据。

## 7. 0.10 候选版验证增量

自动回归覆盖新旧格式、任务引用与依赖、验收覆盖、职责约束、切片批准、多包共存、目录迁移和派生漂移。EVAL-013—019 新增行为规格；需要未参与起草者实际执行，当前不能视为通过。跨项目真实试点至少补 new/enhancement/delta、单人/多人职责、Web 之外的软件项目。阅读版需实际打开检查；不得只证明生成了 HTML 文件。
