# 前置生命周期

## 1. 适用方式

生命周期描述从原始需求到开发准备包的逻辑状态，不要求机械地按文档顺序一次完成。阶段可以迭代、回退、并行精化，但所有适用的退出条件必须在对应切片的 Development Ready 前满足。

轻量和标准路线可以合并阶段及产物；完整路线应保留每个阶段的明确结论。

## 2. 阶段总览

| 阶段 | 核心问题 | 主要产物 | 退出条件 |
| --- | --- | --- | --- |
| P0 输入与基线 | 我们依据什么事实、为哪个项目工作 | 输入卡、来源索引、项目根目录、包身份、现状、未知项 | 来源、项目归属、范围和证据状态显式 |
| P1 问题与范围 | 为什么做、为谁做、什么不做 | 问题陈述、目标、成功指标、范围 | 问题与边界获得确认 |
| P2 需求规格化 | 系统必须表现出什么行为 | 需求、规则、异常、验收条件 | 关键语义无需开发者猜测 |
| P3 业务建模 | 对象、状态和完整流程如何运行 | 术语、对象、状态机、流程、补偿 | 对象、规则和流程一致 |
| P4 能力与模块 | 能力如何形成软件边界 | 能力图、模块责任卡、入口归属 | 所有权唯一、边界可解释 |
| P5 模块交互 | 各边界怎样协作 | 关系图、时序图、交互矩阵、能力目录 | 成功和失败链路闭合 |
| P6 架构与契约 | 哪些全局和跨边界约束必须先定 | 架构决策、API/事件、数据和质量约束 | 并行开发无需重定跨边界规则 |
| P7 纵向切片 | 如何拆成可独立实现的业务结果 | 路线图、切片卡 | 切片有价值、边界和验收 |
| P8 开发步骤 | 具体按什么依赖顺序开发 | 任务卡、依赖图、团队映射 | 每项任务可直接领取和判断完成 |
| P9 联调与验收 | 如何证明模块和端到端结果 | 模块验收、联调矩阵、未验证项 | 验收责任和证据要求明确 |
| P10 自验与交付 | 准备包是否可交付 | 包清单、自验报告、追踪矩阵、Ready结论 | 达到质量门且项目内产物可追溯 |

## 3. P0 输入、现状、模式与路线判定

### 输入

- 原始需求和补充说明；
- PRD、原型、代码、接口、数据或外部文档；
- 项目约束和团队画像；
- 已知决策、争议和未决项。

### 活动

1. 按 `protocol/source-governance.md` 建立来源索引，区分权威输入、辅助证据和排除输入；旧资料默认不继承。
2. 记录当前真实行为，避免把期望状态当成现状。
3. 把关键内容标为事实、决策、假设、未知或阻塞。
4. 选择 new/enhancement/delta 工作模式，再按本次变化选择轻量、标准或完整路线。
5. 判断是否缺少足以改变后续设计的关键输入。
6. 按 `protocol/output-management.md` 确认目标项目根目录、准备包身份、输出位置和初始版本，并在首次写入前通过路径预检。

### 输出

- `templates/00-intake-and-context.md`；
- `templates/package-manifest.json` 创建的项目内包清单；
- 选定路线及理由；
- 阻塞项和非阻塞未知项。

### 退出条件

- 所有关键来源可追溯；
- 权威、辅助和排除来源集合互斥，用户确认规则具有稳定 ID；
- 当前状态和目标状态没有混用；
- 阻塞项不会被转换成未经批准的假设；
- 正式准备包具有确定的项目归属，不能确认项目根目录时不落盘为正式包。

## 4. P1 问题、价值与范围

### 活动

- 明确目标用户、问题、现有替代方式和问题后果；
- 区分用户问题与用户提出的实现方案；
- 定义目标、成功指标、范围和非目标；
- 识别利益相关者及相互冲突的目标；
- 记录期限、预算、合同、法律或组织约束。

### 退出条件

- 需求具有明确目标，而不是只有功能名；
- 成功指标可观察；
- 范围足以支持后续分析；
- 决策责任人清楚。

## 5. P2 需求规格化

每项重要需求至少覆盖：参与者、触发条件、前置条件、输入、主要流程、异常流程、状态变化、权限、业务规则、输出、非功能要求和验收条件。

应主动检查：

- 空数据与初始状态；
- 加载、处理中和长耗时操作；
- 业务拒绝和技术失败；
- 超时、重复提交、并发和取消；
- 权限不足和敏感操作；
- 兼容、迁移和外部依赖失败；
- 人工介入、补偿和恢复。

### 退出条件

- 关键业务语义没有留给开发者自行猜测；
- 验收条件描述结果，不绑定非必要实现方式；
- 未决项具有业务影响和处理责任人。

## 6. P3 业务建模

### 活动

- 建立统一术语和同义词/歧义词表；
- 识别核心对象、值、角色及其生命周期；
- 为有状态对象建立状态机和允许动作；
- 描述用户流程、系统流程和人工流程；
- 描述成功、拒绝、失败、超时、取消、部分成功和补偿路径；
- 明确外部参与者和系统边界。

### 退出条件

- 同一业务概念在需求、流程和状态机中含义一致；
- 关键状态都有进入、退出和终止条件；
- 失败后系统处于可解释状态。

## 7. P4 产品能力与软件模块拆解

依次完成：

1. **产品能力拆解**：产品需要具备哪些独立业务能力。
2. **软件模块拆解**：哪些能力共享同一领域语言、规则和数据所有权。
3. **入口归属**：页面、API、管理操作、后台任务、定时任务和外部回调由谁主责。

每个模块使用 `templates/03-module-card.md`。

### 边界规则

- 模块围绕业务能力而不是人员数量、前后端层次或数据库表拆分；
- 每个核心数据只有一个模块拥有写入语义；
- 一个入口可以组合多个模块能力，但只有一个组装主责；
- 其他模块通过公开能力、契约或可复用组件协作；
- 团队分工在模块边界形成后映射。

### 退出条件

- 模块职责和非职责都能清楚陈述；
- 数据和入口所有权唯一；
- 依赖能够绘制且没有未解释循环；
- 团队约束没有反向制造错误业务边界。

## 8. P5 跨模块交互建模

这是完整路线的必备阶段，标准路线在涉及模块边界时也必须执行。

每条关键链路建立：

- 端到端流程负责人；
- 调用方和能力提供方；
- 业务语义（命令、查询、已发生事实或人工交接）与传递模式（同步、异步、批处理）分别说明；
- 当前逻辑通道，以及技术形态变化后仍须保持的契约边界；
- 关键输入输出和状态变化；
- 事务提交位置；
- 幂等、超时、重试、顺序和版本要求；
- 拒绝、失败、重复、乱序、丢失、取消和补偿；
- 权限、租户或信任边界；
- 契约所有者和评审方。

完整路线对适用交互形成带 `COMM-*` 标识的通信模式目录；以下各项须给出结论或不适用理由：

- 同步命令和查询；
- 异步事件、消息投递及消费确认；
- 页面或 API 的跨模块读聚合；
- 外部系统的请求、回调、轮询或人工交接；
- 事务、一致性、重复投递、部分成功和补偿边界；
- 请求与消息用于身份、租户、Trace、幂等和版本的公共语义。

产物使用 `templates/04-interaction-catalog.json`、`templates/05-architecture-and-contracts.md` 和必要的图。存在复杂关系时至少提供一张有业务意义且已呈现的拓扑、时序、状态或依赖图；Mermaid 为默认源格式，项目已有绘图方式同样可用；涉及三个及以上组件、异步回调、状态跨越或复杂依赖时，应按不同认知问题增加相应图，而不是把全部关系塞进一张图。图负责关系总览，`COMM-*`、`INT-*` 和 `CON-*` 表负责精确语义。不得用图替代错误、权限、可靠性和所有权说明。

### 退出条件

- 每条主链路和关键失败链路都能闭合；
- 没有模块直接依赖另一个模块的私有数据或实现；
- 没有无人负责的端到端流程或契约。
- 图、通信目录、交互目录和正式契约没有冲突。

## 9. P6 架构约束与正式契约

只定义影响系统整体、跨团队协作或关键风险的内容：

- 技术栈和兼容基线；
- 工程、仓库和运行边界；
- 模块依赖规则；
- 前后端、模块间和外部接口；
- 请求、响应、事件和错误语义；
- 数据所有权、关键模型和迁移约束；
- 身份、权限、信任和敏感数据边界；
- 事务、幂等、精度、时间和版本规则；
- 性能、可靠性、安全、兼容和可维护性目标；
- 影响整体实现的重要决策及取舍。

### 退出条件

- 各方可并行开发公开边界；
- 契约足以生成 Mock 或契约测试；
- 没有提前规定不必要的内部实现。

## 10. P7 纵向交付切片

每个切片应交付一个可观察的用户或系统结果，并包含实现该结果必要的入口、业务能力、数据变化、跨模块契约和验收条件。

不得仅按“所有前端、所有后端、所有数据库”横向切割。确需基础工作时，应说明其解锁的首条端到端链路。

使用 `templates/06-delivery-slice.md`。

### 退出条件

- 每个切片范围可控；
- 依赖、可并行关系和演示结果清楚；
- 大型需求已经拆到单次开发上下文可控制的粒度，但没有碎成无业务意义的小任务。

## 11. P8 开发步骤与团队映射

每项任务可使用 `templates/07-development-task.json` 起草；交付时登记进 `templates/delivery-plan.json`，说明目标、上下文、范围、非目标、依赖、边界、预期结果、验收条件、风险和联调点。

团队约束影响：

- 负责人和协作者；
- 任务大小和并行度；
- 关键路径和交接点；
- 能力缺口和必要支持；
- 工作量平衡和排期风险。

团队约束不影响已经确认的合理业务边界。

### 退出条件

- 每项任务可以被独立领取；
- 任务依赖无循环；
- 没有要求开发模型使用指定 Skill、Agent 或工具；
- 不可行的团队约束已经显式报告。

## 12. P9 联调与验收准备

使用 `templates/08-integration-and-acceptance.md` 明确：

- 模块独立验收；
- 跨模块契约验收；
- 端到端联调链路；
- Mock 与真实系统的使用边界；
- 正常、失败、超时、重复、并发、补偿和安全场景；
- 数据一致性与对账；
- 产品验收、测试评判和客户效果评判的责任边界；
- 开发后才能验证的项目。

### 退出条件

- 每项关键需求都有对应验收方式；
- 模块完成和产品完成没有混为一谈；
- 未验证项不会被提前宣称通过。

## 13. P10 自验与交付

按 `protocol/self-validation.md` 执行自验，生成 `templates/10-self-validation-report.md`，并按 `protocol/development-ready.md` 给出结论。同步更新 `package-manifest.json` 中的版本、路线、来源策略、基线状态、readiness、可开发范围和实际产物路径。

若存在阻塞，按 `protocol/clarification-and-baseline.md` 集中提问并在收到答案后完成全链回写。在项目既有入口追加本包导航，运行项目准备包校验器。

按新版质量门确定已批准且就绪的切片授权范围后，以目标项目内的准备包路径和明确版本交付，本体系停止。后续开发执行者自主选择实现方式。
