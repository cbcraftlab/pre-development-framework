# 开发准备包输出规则

框架只保存规则、模板和合成示例；真实准备包跟随项目或用户明确指定的项目文档根目录。

默认：`<project-root>/docs/pre-development/<package-id>-<package-slug>/`。已有项目可选择自己的文档目录。尚无代码仓库的新产品可以使用用户指定、身份明确的文档根目录；无法确认目标目录时只输出分析草稿，不宣称已生成正式包。

写入前路径预检：确认目标根目录实际存在，解析输出路径在其内部，避免同名副本、目录逃逸或覆盖来源；不自动修改既有入口正文。绝对路径只传给本机工具，清单使用稳定 project_id 和相对 package_path。

包用 `package_version` 记录每次影响语义、分工或授权的修订。最小逻辑输出：清单、上下文、需求正文和开发计划；轻量结论可以压缩，但已授权任务仍需可机械校验的依赖/验收。文件仅因负责人或可读性需要拆分，不强迫每个阶段一个文件。

清单 `artifacts` 登记正式文件；`context_artifact`、`plan_artifact`、`primary_artifact` 指向唯一事实位置。标准/完整路线默认交付 HTML 阅读版；项目已有能正确呈现表格和图的工具时可以用 `readable_waiver` 记录工具、验证证据与责任人，不能只写“不需要”。轻量路线也要说明实际阅读方式。

复杂关系应有可见图，不能把 Mermaid 源码当作已呈现图。清单以 `diagrams` 登记源与图文件以及核对证据；图的业务一致性由复核证明。无复杂关系时允许说明不适用，不为了满足检查器制造架构。

用 `python3 scripts/validate_project_package.py --project-root <root> --package-dir <relative>` 校验。主 Markdown 位于包根目录，HTML 与其同目录；内部附件可分目录。内容版本变化后重建阅读版，检查受影响任务。哈希只用于检测来源和派生产物漂移，不用于声称业务语义正确。

旧版 0.9.0-candidate.5 包走冻结的兼容校验，不自动升级。迁移先备份并明确新项目身份、旧基线引用、团队职责、任务/验收映射；无法恢复的字段标未知。新版包只能在授权转换后生效，不能靠替换版本号获得批准。迁移见 [增量与证据协议](change-and-evidence.md)。
