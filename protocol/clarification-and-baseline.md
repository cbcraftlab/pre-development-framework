# 集中澄清、决策回写与基线冻结

## 1. 目的

`Not Ready` 不是流程终点。框架必须把发现的问题稳定推进为：集中提问、责任人回答、跨产物回写、重新自验和明确的开发基线状态。

## 2. 哪些问题必须澄清

只有会改变以下内容的问题才阻塞相应开发范围：

- 用户可观察行为或首发范围；
- 资金、权限、安全、隐私或不可逆数据规则；
- 模块、入口或核心数据所有权；
- 跨模块或外部接口契约；
- 状态机、事务、幂等、精度、时间或兼容语义；
- 团队和期限是否使计划不可执行。

私有函数、局部变量、内部类、调试方式、模型、Skill、Agent 和无跨边界影响的内部实现不进入产品澄清。

## 3. 集中澄清清单

每个问题使用稳定 `Q-*` 标识，并包含：

| 字段 | 要求 |
| --- | --- |
| 冲突或缺失 | 准确描述，不把推断伪装成事实 |
| 来源 | 指向产生冲突的 `SRC-*`、`USR-*` 或现状证据 |
| 可选口径 | 只列证据支持或责任人可合理选择的方案 |
| 影响范围 | 需求、规则、模块、契约、任务和验收 ID |
| 风险等级 | 普通 / 高后果 |
| 决策责任人 | 明确谁有权回答 |
| 最迟决策点 | 在哪个切片或任务前必须关闭 |
| 是否可隔离 | 若可隔离，说明不受影响的开发范围 |

问题应一次性按主题集中提出。不得为了追求 `Ready` 而诱导责任人接受模型默认值。

## 4. 回答回写闭环

收到责任人回答后，必须执行影响扫描并同步更新：

```text
来源/用户确认记录
-> 需求和业务规则
-> 对象、状态与流程
-> 模块、入口和数据所有权
-> 交互与正式契约
-> 切片和开发任务
-> 验收条件与追踪矩阵
-> 阻塞清单、自验结论和包清单
```

只把问题标记为“已回答”，但没有更新上述受影响位置，视为澄清闭环失败。

## 5. 材料、批准与授权

按 [质量门](development-ready.md) 独立记录材料就绪、基线批准和切片授权。candidate 可以 ready，但不得授权。未决问题只阻塞受影响切片和其依赖，不必把整个包的可开发范围清零。

## 6. 冻结与变更

先完成材料自验、需要的隔离复读和结构校验，再请相应责任人确认范围、契约与验收，登记批准证据与授权任务。一个人可以承担多个责任角色，不强制增加审批层级。

答案只回写受影响条目，其他位置引用稳定 ID；涉及产品口径、公开契约、任务或验收的变化升版，并使受影响切片批准待复核。变化清单与基线引用遵守 [增量协议](change-and-evidence.md)。
